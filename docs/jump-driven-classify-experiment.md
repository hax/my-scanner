# 跳跃驱动的分类 pass：实验记录（2026-09-15，已否决回退）

## 起点

用户洞察：**向量化的典型收益在于长跳跃**——字符串尾部、模板分段、注释结束、
换行这些都是可能跨越许多字节的跳跃，而它们与 ident/ws 一样是"找小集合字符"
问题，理应在第一轮 SIMD（分类 pass）里尽量多做，甚至可配十字分解等 trick
做多平面检测。

## 设计（已完整实现并验证正确性）

- 跳跃起点无歧义性：相邻 `//`、相邻 `/*` 必为注释（词法规范无反例），
  quote 起点由顺序状态遮蔽（字符串/注释/模板内部的假起点不会触发）。
  **唯一误触发在正则体内**（`/\/\.//g` 中的 `//`、`/'/` 的引号）。
- classify pass 维护顺序跳跃状态：遇跳跃起点直接调用现有跳跃函数
  （scanString / scanTemplate / tryComment）得到 [start, end)，区间从
  候选位图剔除、token 记入 jumps 表；阶段 2 命中 jumps 直接产 token。
- 正则误触发自愈：正则整体是单 token，阶段 2 消费正则后丢弃被覆盖的
  jumps；**溢出段**（行注释型假跳跃吞到行尾、越出正则边界）通过
  restoreCandidates 用基础规则 OR 回候选位（只加不减，多恢复的假候选
  由 pos 跳过兜底）。

实现过程修复的三个 bug（模式存档）：

1. 跳跃起点位保留在 masks 中导致触发循环重入死循环——触发时临时清出、
   循环结束后恢复。
2. 假跳跃溢出正则边界的剔除无法由"丢弃表项"撤销（位图已写）——必须
   回滚候选位。
3. 回滚写回 masks 但主循环内层用的是块入口拷贝——恢复不可见；寄存器
   迭代 + 恢复时重载，或原地迭代（后者引入 store-load 依赖，慢）。

**正确性达成**：七个样本（含 cn-dense / line-comments / strings 盲区样本）
与 tsc 的 token 级差分测试全部一致。

## 性能结论（否决）

| 指标 | 对照（无跳跃） | 跳跃驱动 |
| --- | --- | --- |
| classify 自身 | 4.5 GB/s | **2.0-2.5 GB/s** |
| typescript.js 端到端 | 84.2 Mtok/s | 66-69（-18%） |
| line-comments.js 端到端 | 80.6 | 66-67（-17%） |

line-comments 的账本最能说明问题：cls +0.27ms（跳跃工作搬进来 + 检测税）
vs 阶段 2 -0.27ms（tryComment/lineEnd 挪走）——**工作等量搬迁，零净收益**；
typescript 则纯付检测税。减法实验（去掉 quote 跳跃只留注释）确认每块的
跳跃检测 mask（quote/slash/star 的 5 个 eq）加上巨函数的寄存器压力退化，
大于任何场景的收益。

## 根本教训

yuku-main 注释向量化的收益来自**单阶段架构**：跳跃读到的字节只被触碰
一次。两阶段架构里把跳跃搬进 classify，同一区间仍会被 cls 的块循环与
跳跃函数共同触及，本质是换位置付同样的钱，还要加检测税。

「长跳跃前移」的洞察本身是对的——它在单阶段或真正融合的架构下才能完全
兑现。而阶段融合已被两次实验否决（缓存行为：无依赖的线性 SIMD 扫 +
L1 驻留位图的两阶段分离更快）。要吃下这个收益，需要的不是修补，而是
**重新设计两阶段的分工**——例如单阶段 + SIMD 候选缓冲（候选位图按块
在寄存器/栈上产出并立即消费，不物化全文件数组），这是与现有两阶段不同
的第三种形态，值得作为独立的大方向评估。
