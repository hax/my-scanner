# 实验方法论：会话中沉淀的教训

本项目每个优化都走「假设 → 实现 → 测试 + tsc 差分 → bench 裁决」的循环，
裁决标准是数据而非直觉。以下是循环本身踩过的坑，供后续实验避雷。

## 1. ReleaseFast 下 profile 的行号归因不可靠

案例：sample 显示 `unicodeWhitespaceLen` 占 13% 采样，追查后发现该文件
（lib.dom.d.ts）总共只有 **45 个非 ASCII 码点**——量级上不可能。
0.04% 的真实工作量被归因到 13%，是深度内联后 DWARF 行号错乱的产物。

**规则：profile 指出热点后，先做量级数学（调用次数 × 单次成本 ≈ 占比），
对不上就怀疑归因，不要怀疑代码。** 更可靠的定位手段是插入计数器或
分项计时，而不是继续看采样树。

## 2. 指令数减少不必然转化为吞吐

案例一：`|0x20` fold 把 identPartMask 从 ~14 条压到 ~10 条指令——
吞吐零变化。案例二：块内 ws 判定内联省去函数调用——零变化。
瓶颈可能在别处（依赖链、load 端口、循环开销、寄存器压力），指令数
只是纸面证据。

**规则：指令数优化必须过 bench，无实测收益即回退（数据说话）。**

## 3. 标量基线的写法决定 A/B 的公平性

案例：whitespaceMask 的 SIMD vs 标量只有 **2.2x**，而 identPartMask 是
19-24x——因为 whitespace 的标量循环被 LLVM **自动向量化**到接近手写
SIMD，另两个原语的标量版因 `m |= 1 << j` 的变量移位阻止了 autovectorize。

**规则：宣称 SIMD 加速比之前，先确认标量基线没被（或不曾被）编译器
自动向量化；被自动向量化的模式，手写 SIMD 增益有限。**

## 4. 巨函数的寄存器压力退化是隐形税

案例：跳跃驱动的 classifyPass 把换行、unicode 修正、跳跃触发全部
塞进一个函数（~250 行）——自身从 4.5 掉到 2.0-2.5 GB/s，其中只有
~15% 可由新增指令解释，其余是调度/寄存器分配退化。

**规则：往热循环里加逻辑时，盯住"函数变巨"的隐性成本；必要时拆小
函数（换行计算、修正、触发各自独立），让 LLVM 局部优化。**

## 5. 位图/区间类状态「写后不可撤销」的操作要预留回滚

案例：跳跃驱动实验中，假跳跃（正则内的 `//`）剔除了位图区间，
后来发现区间溢出正则边界——丢弃表项不恢复位图，丢 token。
修复是 restoreCandidates 用基础规则 **OR 回**（只加不减，多恢复的
假候选由消费端 pos 跳过兜底——方向性安全）。

**规则：预写状态（剔除/标记）在可能误判的场景下，回滚机制要走
「宁可多勿少」的安全方向，让既有的兜底路径消化多余部分。**

## 6. 清理/重构可能误删活代码，行为测试网是最后防线

案例：一次正则清理误删了 danglingUnicodeWs 最常用的分支
（跨块 U+2000-200A/U+2028/29 形态），潜伏多轮后被**随机交叉验证**
撞出（此前固定用例恰好没覆盖该组合）。同类：批量文本替换把 switch
分支弄丢、`'a'..'z'` 半开区间漏掉 'z'。

**规则：(a) 随机/模糊交叉验证要进常设测试（我们用确定性 PRNG 的
200 轮随机字节流，两实现逐位一致）；(b) 重要的语义分支配防回归用例；
(c) 批量替换脚本后必跑全量测试。**

## 7. 语料盲区会系统性扭曲优化方向

案例：四个基准语料几乎纯 ASCII（lib.dom.d.ts 仅 45 个非 ASCII 码点），
导致 unicode 路径长期被当"罕见冷路径"处理；补齐中文/行注释/字符串
密集三语料后，实测落后 yuku-main 0.68-0.81x——暴露出 lineEnd 标量循环、
模板子表达式标量扫描等真实遗漏，还抓出一个潜伏的 dangle 分支 bug。

**规则：优化前先问语料谱系覆盖了什么——token 密度（minified ↔ 注释
密集）、unicode 密度、字符串/注释密度。缺的维度先补语料再谈优化。**

## 8. 快速放弃 vs 死磕的判据

无收益实验的正确动作不是立即回退，而是先回答"为什么没收益"——
答案要么指向真正的瓶颈（换方向再试），要么证明该方向已到顶（回退）。
案例：fold 技巧无收益时若追问"瓶颈在哪"，会更早发现巨函数退化问题；
跳跃前移实验正是靠 line-comments 的 ±0.27ms 账本定位到"工作等量搬迁"
的本质，才得出单阶段/两阶段的架构性结论（见 architecture.md）。
