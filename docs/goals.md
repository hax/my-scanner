**以下是设计和实现的出发原点，未经 hax 确认不得修改。**

## 目标

1. **高吞吐**：用 SIMD 系统性地压榨 JS/TS token 化的性能上限
2. **容错性**：任何输入都不中断扫描 —— 输出的是 token 的起始位置和种类，对应的字节范围仍可能有未闭合、非法字符、坏 UTF-8 等情况。合法性校验、修复或丢弃策略等留给 parser / linter 等按需开启或自行处理，即按需或延后支付相关成本，并能适应以下场景：
    - 语法高亮、代码搜索、词法级别的宏等：只需要 token 流；
    - LSP：编辑器里的代码永远处于半成品状态（打了一半的字符串、未闭合的注释/模板），切分必须立刻可用并行为稳定；
    - 代码转换 / 生成流水线：中间产物可能带轻微语法错误，允许下游处理而不是失败；
    - 语言特性扩展：新语法应被切分成边界合理的 token，而不是崩溃或错位。

## 非目标

- **罕见输入和极端分布形态的性能**：为常规样本和典型特例优化，可以牺牲罕见情况下的性能，例如可以由 parser 发出重新扫描指令或进行二次切分。
- **100% spec 合规**：为正确输入优化，对于不合理输入（语法错误、语义错误、必然导致运行时错误的输入）可以输出不符合 spec 的切分结果（某种程度上的 [GIGO](https://en.wikipedia.org/wiki/Garbage_in,_garbage_out)）。

允许对上述非目标范畴做实现取舍（换取性能和容错），但**每个取舍必须登记在 [tradeoff](tradeoff.md) 里**：输入形态、my-scanner 行为、spec/tsc 行为、触发条件为何可接受。

注意区分：与 tsc scanner 的**口径差异**（某些设计选择，如 `>` 家族合并与否）不是 tradeoff，见 [correctness](correctness.md)。
